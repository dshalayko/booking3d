# Инструкции по разработке

Этот файл фиксирует актуальные правила для изменений в проекте. Историю
первоначальной реализации и причины старых решений см. в `PLAN.md`, пользовательский
сценарий — в `GUIDE.md`.

## Доменные инварианты

1. Один пользователь может иметь не более одной активной работы во всей системе.
   Статусы `printing` и `done_wait` оба считаются активными: новая работа или бронь
   возможна только после освобождения машины.
2. Один пользователь может иметь не более одной активной брони во всей системе.
   Свою забронированную машину разрешено занять раньше, если это не пересекается с
   чужими окнами; это продолжение той же задачи, а не вторая работа.
3. Очереди в продукте больше нет. Свободную машину занимают сразу, нужное время
   выбирают в календаре. Таблица `queue` и чтение её записей в журнале сохранены
   только для исторических данных; новые HTTP-маршруты, команды и записи очереди
   добавлять нельзя.
4. Таймер не освобождает машину. После `eta_at` работа переходит в `done_wait`, а
   машину освобождает человек после проверки стола или переговорной.
5. Транзакцией и уведомлениями управляет вызывающий слой. Сервисы домена не делают
   `commit()` и не отправляют сообщения самостоятельно.
6. Параллельные действия одного пользователя сериализуются блокировкой строки
   `users`; ограничения PostgreSQL остаются последней защитой от гонок.

## Как вносить изменения

- Начинайте с сервиса в `app/services/`; HTTP- и Telegram-обработчики должны быть
  тонкими адаптерами к одному и тому же доменному сценарию.
- Пользовательские строки добавляйте одновременно в `app/texts/ru.py` и
  `app/texts/en.py`. Не размещайте тексты прямо в обработчиках или шаблонах.
- Изменение модели сопровождайте новой миграцией Alembic. Старые миграции после
  публикации не переписывайте.
- В запросах доски и расписания ограничивайте выборку текущим помещением или
  набором машин; не загружайте весь парк ради одного экрана.
- Не возвращайте удалённые сценарии очереди через совместимость интерфейса:
  совместимость нужна данным журнала, а не старым действиям.

## Проверка

Перед завершением изменения выполните:

```bash
./run.sh check
```

Минимум для быстрой локальной проверки без обёртки:

```bash
.venv/bin/python -m ruff check .
.venv/bin/python -m pytest -q
```

Новая бизнес-логика должна иметь тест на успешный сценарий, отказ и, если она
меняет лимиты или уникальность, на параллельные запросы либо ограничение базы.
